## 3. 实现设计

### 3.1 收藏（书签）联系人

设计思路：原帖对这一项给分最高（25 分），要求是「能标记重要联系人，并且能方便地再次访问」。因此我没有只做一个孤立的开关，而是把收藏设计成贯穿数据层、接口层、界面层与导出层的完整能力：数据层用布尔字段持久化，接口层用一个幂等的 PATCH 切换，界面层提供独立入口和视觉标识，导出层把状态写进 Excel 列——这样收藏不是「点一下就看不见」的临时标记，而是可筛选、可排序、可携带、可批量处理的稳定属性。

- 数据模型里为每位联系人增加 `bookmarked` 布尔字段，切换走 `PATCH /api/contacts/:id/bookmark`，不传值时自动取反。
- 前端侧栏提供「我的收藏」独立入口与实时计数，卡片星标 + 「已收藏」徽标让收藏状态一眼可辨；排序支持「收藏优先」。
- 收藏状态写入 Excel 的「收藏」列（`是`/`否`），导入时兼容 `是 / 否 / true / 1 / Y / ★` 等写法，保证导出再导入不丢状态。
- 支持勾选多人批量收藏 / 取消收藏。

关键代码（后端 `server/routes/contacts.js`）：不传 `bookmarked` 时取反，传了布尔值时按指定值设置，因此同一接口既能「点星标切换」也能「批量设为已收藏」，不用为两种交互各写一个接口。

```javascript
router.patch('/:id/bookmark', wrap((req, res) => {
  const current = store.find(req.params.id);
  if (!current) return fail(res, '联系人不存在', 404);
  const next = req.body && typeof req.body.bookmarked === 'boolean'
    ? req.body.bookmarked
    : !current.bookmarked;
  return ok(res, store.setBookmark(req.params.id, next),
    next ? '已加入收藏' : '已取消收藏');
}));
```

批量操作复用同一套仓储逻辑（`POST /api/contacts/bulk`，`action` 支持 `bookmark / unbookmark / delete`），前端勾选后一次请求完成，避免逐条请求造成的闪烁与竞态。

### 3.2 多种联系方式

- `contactMethods` 是一个数组，元素为 `{ id, type, label, value, primary }`，类型覆盖手机、座机、邮箱、微信、QQ、微博、领英、社交账号、地址、网站、其他共 11 类。
- 编辑表单可动态增删行，可指定「主要联系方式」；详情页按类型显示图标并支持一键复制。
- 搜索时把所有联系方式的值拼进检索文本，因此输入手机号也能查到对应联系人。
- 后端对类型做白名单校验并对「主要」数量做归一化，避免脏数据。

数据结构（`data/contacts.json` 中的真实一条记录，林晓有 2 个手机 + 邮箱 + 微信）：

```json
{
  "id": "c-1001",
  "name": "林晓",
  "bookmarked": true,
  "contactMethods": [
    { "id": "m-1001a", "type": "phone",  "label": "手机",     "value": "13800001111", "primary": true },
    { "id": "m-1001b", "type": "phone",  "label": "备用手机", "value": "13900002222", "primary": false },
    { "id": "m-1001c", "type": "email",  "label": "邮箱",     "value": "linxiao@example.com", "primary": false },
    { "id": "m-1001d", "type": "wechat", "label": "微信",     "value": "linxiao_dev", "primary": false }
  ]
}
```

前端表单用「动态行」实现：新增一行就是往数组里 push 一个对象，删除行则按 `id` 移除；`primary` 用单选逻辑保证最多一个主要联系方式。列表页和详情页对 `contactMethods` 做 `map`，按 `LABEL_OF[type]` 显示中文标签与对应图标，点击可一键复制 `value`。搜索时后端把姓名、公司、标签以及所有 `contactMethods[].value` 拼成一条检索文本，所以输入手机号、邮箱或微信号都能命中对应联系人。

### 3.3 Excel 导入导出

- **导出**：每个联系人一行；姓名、收藏、公司、部门、职位、生日、标签、备注各占一列；联系方式按类型分列，同类型多条时自动生成 `手机`、`手机2`、`邮箱2` 等列，列数按数据动态扩展。附带「字段说明」工作表，并设置冻结表头、自动筛选与隔行底色。导出接口复用列表的筛选参数，实现「导出当前筛选结果」。
- **导入**：采用「上传解析（只解析不写库）→ 前端预览 → 选择重复策略 → 确认写入」三步，避免误操作直接污染数据。
- **表头兼容**：支持中文/英文别名、带序号列名、`联系方式` 混合列（自动判断邮箱/手机/网址）；缺「姓名」列或旧版 `.xls` 给出明确报错；未识别列安全忽略并在预览中提示。
- **重复策略**：`append` 全部新增、`merge` 按姓名合并并去重联系方式、`skip` 跳过同名。
- **往返一致性**：导出的文件可以直接再导入，收藏状态与多条联系方式不丢失，已写入自动化测试。

关键代码——动态列生成（`server/services/excel.js`）。这是整个导入导出的难点：原帖要求「一人一行、每类信息一列」，但一个人可能有两个手机号。做法是统计每类联系方式的最大条数，按需扩展出 `手机`、`手机2` 等列，导入时再把数字后缀归一化回同一类型：

```javascript
function methodColumns(contacts) {
  const maxCount = new Map(METHOD_TYPES.map((t) => [t.value, 1]));
  for (const c of contacts) {
    const count = new Map();
    for (const m of c.contactMethods || []) {
      count.set(m.type, (count.get(m.type) || 0) + 1);
    }
    for (const [type, n] of count) {
      maxCount.set(type, Math.max(maxCount.get(type) || 1, n));
    }
  }
  const cols = [];
  for (const type of METHOD_TYPES) {
    const n = maxCount.get(type.value) || 1;
    for (let i = 1; i <= n; i += 1) {
      cols.push({
        kind: 'method',
        type: type.value,
        header: i === 1 ? type.label : `${type.label}${i}`,
      });
    }
  }
  return cols;
}
```

关键代码——两步导入（`server/routes/excel.js`）。解析与写入彻底分开，`/preview` 只把文件解析成联系人数组返回给前端预览，`/commit` 才真正落库，从而避免误上传直接污染数据：

```javascript
router.post('/preview', upload.single('file'), wrap(async (req, res) => {
  if (!req.file) return fail(res, '请选择要导入的 .xlsx 文件');
  const parsed = await excel.parseWorkbook(req.file.buffer);
  return ok(res, { ...parsed, fileName: req.file.originalname });
}));

router.post('/commit', wrap((req, res) => {
  const { contacts, duplicate = 'append' } = req.body || {};
  if (!['append', 'skip', 'merge'].includes(duplicate)) return fail(res, '无效的重复处理策略');
  const report = store.commit(contacts, duplicate);
  return ok(res, report);
}));
```

## 6. 协作问题与解决方案

> 每位成员从自己的视角写至少 2 条真实遇到的问题，不要照抄。下面按各自负责的模块写实，另一篇博客请用自己的口吻重写。

**成员 A（后端与数据）：**

1. **问题：两人同时改数据文件时出现覆盖。** 起初前后端都直接读写 `data/contacts.json`，联调时一边在测试导入、一边在点收藏，后写的一次把前一次的结果整个覆盖掉。
   **解决**：约定持久化只由后端负责，前端一律走 API；后端写入改为「先写临时文件、再 `rename` 原子替换」，保证任何时刻读到的都是完整文件，不会出现半截 JSON。
2. **问题：Excel 中一个人有两个手机号，固定列会丢数据。** 原帖要求「一人一行、每类信息一列」，但若给「手机」只留一列，第二个号码无处可放；若允许多行，又违反「一人一行」。
   **解决**：改为按类型统计最大条数动态生成列——有人有 2 个手机就多出「手机2」列；导入时用 `normalizeHeader` 去掉表头的数字后缀，把「手机」「手机2」都归一化为 `phone` 类型写回数组。往返测试专门断言这条不丢数据。
3. **问题：导出的 Excel 莫名其妙多出空行，导致导出再导入往返测试失败。** 排查发现是样式函数里用 `sheet.getRow(r)` 预访问了还不存在的行，ExcelJS 会把这些行真正创建出来。
   **解决**：把样式拆成 `styleSheet()`（只处理表头）和 `styleBody()`（数据写完后再用 `eachRow` 遍历），空行问题消失，33 项测试全部通过。

**{{队友姓名（成员 B，前端与体验）}}：**

1. **问题：导入直接写库，测试时反复污染演示数据。** 最初上传 Excel 后立刻入库，误传一次就得手动把 10 条演示数据恢复回来，调试成本很高。
   **解决**：拆成 `preview` / `commit` 两步——上传后只解析并在弹窗里预览识别到的联系人、跳过原因和重复项，用户确认并选择重复策略后才写入。前端据此设计了三步导入向导。
2. **问题：窄屏下侧栏挤占内容，手机上按钮被挤出屏幕。** 桌面端固定侧栏在 390px 宽的手机上把卡片区压得只剩一半。
   **解决**：`@media (max-width: 860px)` 下把侧栏改为抽屉式菜单，卡片单列排布，表格改为横向滚动，顶部三个核心按钮（新建 / 导入 / 导出）保留为图标按钮，移动端实测可用。
3. **问题：深色主题切换后图标仍是黑色，在深色背景上看不清。** 图标是内联 SVG，写死了 `fill`。
   **解决**：抽出 `hydrateIcons()` 统一在主题切换时重绘图标，`applyTheme()` 同时写入 `localStorage`，刷新后保留用户选择；浅色/深色两套变量共用同一套组件结构。

## 8. 总结

**成员 A：**

这次结对编程让我对一个「看起来简单」的通讯录有了重新认识。真正的难点不在 CRUD，而在三条约束之间的权衡：收藏要「方便访问」，所以做了独立入口、筛选和排序而不只是一个开关；多联系方式要「一人多种」，所以数据模型改用数组；Excel 要「一人一行、每类一列」，这和前者天然冲突，最后靠动态列 + 表头归一化才同时满足。这件事让我明白，写好代码之前先要把需求之间的张力想清楚。

极限编程强调的持续沟通在我们这里体现得很具体：因为提前约定了接口契约和 `docs/代码规范.md`，前后端可以并行开发，联调时几乎没有因为字段命名返工。Git 协作上，我们把提交拆成有意义的三次而不是一次性倒代码，每条 commit message 用 `feat:` / `docs:` 前缀，配合 PR 评审，出问题能快速定位到是哪一次改动引入的。自动化测试从 33 项断言里抓出了 Excel 空行 bug，这比靠肉眼点页面可靠得多——下次我会更早写测试，而不是等功能做完再补。

下次可以改进的地方：一是把数据从 JSON 文件换成真正的数据库，避免云部署冷启动后数据重置；二是演示视频应该更早录制，不要等到截止前一天；三是预估耗时偏低（实际比预估多约 32%），主要低估了联调、部署和举证的时间，下次估算会把这三块单独列出来。

**{{队友姓名（成员 B）}}（请用自己的口吻改写下面这段）：**

我在这一轮主要负责前端页面与交互。最大的收获是学会了「先定契约再写界面」：后端把接口和返回结构先定好，我这边就能用固定的数据形状搭页面，不用等后端全部完成。导入向导是最花心思的部分——把一次性的上传动作拆成预览、选策略、确认三步，既降低了误操作风险，也让我理解了为什么好的交互本身就是在防 bug。

结对编程让我体会到即时 Code Review 的价值：两人对着同一块屏幕讨论一个按钮该放哪里、一个字段该不该必填，比各写各的再合并高效得多。Git 上我学会了用 GitHub Desktop 提交、发起 PR、请队友 Review 再合并，这些流程以前只在课上听过，这次真正走了一遍。

下次可以改进：一是提前做移动端适配，不要等桌面端做完再补救；二是把常用组件抽成可复用模块，减少样式重复；三是多写注释和提交说明，让队友接手时更顺畅。
