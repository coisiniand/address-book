## 一、原帖要求逐条解读

### 1.1 Bookmark Contacts（25 分）

> 原文：*Implement the ability for users to favorite/bookmark contacts. Users should be able to mark important or frequently contacted people and access them conveniently.*

拆成两个得分动作：

1. **能标记**：把重要/常用联系人标为收藏（持久化，刷新后仍在）。
2. **能方便地访问**：必须有独立入口或筛选视图，只有一个 `bookmarked` 布尔字段并不能满足 "access them conveniently"。

另外要注意它和 1.3 的隐含交叉：导出 Excel 时收藏状态属于 "all associated information"，也应能被导出、再导入还原。

### 1.2 Add Multiple Contact Methods（10 分）

> 原文：*Allow users to associate multiple contact details with a single contact, such as phone numbers, email addresses, social media handles, or physical addresses.*

要点：一个联系人 → 多条联系方式，且类型不止一种（电话、邮箱、社交账号、地址）。数据模型必须是数组而非固定几个字段；界面上要能增删。

### 1.3 Import and Export（25 分）★ 重点，本次提问的核心

> 原文：
> - **Export:** *Export each contact and all associated information to an Excel spreadsheet. Each contact should occupy a separate row; each type of information (for example, name or phone number) should occupy a separate column.*
> - **Import:** *Read a correctly formatted Excel file and add the contact information to the address book.*

逐句拆出硬约束：

| # | 约束 | 含义 |
| --- | --- | --- |
| 1 | Excel spreadsheet | 必须是真正的 `.xlsx` 表格文件，不是 CSV / JSON / 网页打印 |
| 2 | each contact + all associated information | 每位联系人的**全部**信息都要出去，包括基本字段、收藏状态、多条联系方式 |
| 3 | a separate row | **一人一行**，不能把一个人拆成多行 |
| 4 | each type of information a separate column | **每类信息一列**（姓名列、公司列、手机列……），不能把信息全塞进一个「详情」列 |
| 5 | correctly formatted Excel | 导入要定义"什么才算格式正确"，所以**必须提供标准模板 + 字段说明**，否则无法验证 |
| 6 | add the contact information | 导入要真正写进通讯录并持久化，不只是解析显示 |

**真正的难点**：约束 3（一人一行）和 1.2（同一人可以有 2 个手机号）天然冲突。若固定写死「手机」一列，第二条号码必然丢失，也就违背了约束 2。本项目的解法是**动态列**：按全体数据中同类型联系方式的最大条数，自动生成 `手机` / `手机2` / `手机3`……，既保持一人一行，也不丢数据；导入时把表头的数字后缀归一化掉，识别回同一类型。

### 1.4 Web Deployment（可选 +15 分）

> 原文：*Deploy the address book on a cloud server, such as Huawei Cloud or Alibaba Cloud. A `localhost` link does **not** count as cloud deployment.*

必须有公网可访问的地址；`localhost` / `127.0.0.1` / 内网 IP 都不算。注意本项目是 Node 后端应用，**GitHub Pages 只托管静态页，不能用来完成这一项**。

**关于"是否必须用阿里云"**：`such as Huawei Cloud or Alibaba Cloud` 是举例，不是指定平台——华为云、阿里云只是两个例子，腾讯云 CVM 或任意有公网 IP 的云主机同样符合；本节标题就写着 `optional`，不做不影响基础 100 分。全文只有这里和评分标准末句提到云部署，别处无任何平台限制。另外开头 checklist 的 "Deployment" 小节指的是 Release 与 Pull Request，不是云服务器。

## 四、导入导出的具体实现（对应 25 分）

### 4.1 导出的列规则

固定列按顺序为：`姓名 | 收藏 | 公司 | 部门 | 职位 | 生日 | 标签 | 备注`。

之后按 `METHOD_TYPES` 的 11 种类型追加联系方式列。若全体数据中某人最多有 3 个手机号，则生成 `手机`、`手机2`、`手机3` 三列；其他人这几列留空。这样**每位联系人始终只占一行**，同时不丢失任何一条联系方式。

工作簿含两个工作表：`联系人`（数据）+ `字段说明`（每列含义与示例）。表头加粗填充、冻结首行、自动筛选、隔行底色，方便老师直接打开核对。

「导出 Excel」菜单有三项：导出当前筛选结果（把搜索/收藏/标签/排序参数一并传给后端，所见即所得）、导出全部联系人、下载标准导入模板。

### 4.2 导入的三步流程

1. **上传解析**（`POST /api/excel/preview`，字段名 `file`）：后端只解析、**不写库**，返回识别到的列、可导入条数、跳过原因与数据预览。
2. **前端预览**：展示识别列 / 被忽略列 / 警告信息 / 预览表格，用户确认无误再继续。
3. **确认写入**（`POST /api/excel/commit`）：提交预览得到的 `contacts` 数组并落盘，返回 `{ created, updated, skipped, errors }` 报告。

之所以拆成 preview / commit 两步，是因为原帖要求 "add the contact information to the address book"，但直接写库在演示和试错时极易污染数据；两步既满足要求又可控。

### 4.3 什么叫「格式正确的 Excel」

模板把规则固化下来：第一行为表头，必须包含「姓名」列；数据从第二行开始；空行自动跳过；姓名为空的行会在预览里给出跳过原因。

表头兼容（`normalizeHeader` 会去空格、括号内容、尾部数字序号并转小写）：

- 中文列名与常见别名：`公司名称` → `公司`、`出生日期` → `生日`、`是否收藏` → `收藏`
- 英文列名：`Name`、`Company`、`Phone`、`E-mail` 等
- 带序号的动态列：`手机2`、`邮箱3` 自动归并到对应类型
- `联系方式` 混合列：用 `;；|` 或换行分隔多条，按内容自动判断邮箱 / 手机 / 网址 / 座机
- 未识别的列：安全忽略，并在预览的 `ignoredColumns` 中提示
- 缺「姓名」列、旧版 `.xls`、超过 20000 行：给出明确中文报错，不改动现有数据

### 4.4 重复策略

| 策略 | 行为 |
| --- | --- |
| `append`（全部新增） | 同名也新增一条 |
| `merge`（合并到同名） | 按姓名合并联系方式并去重，补齐空白字段、合并标签、收藏取或 |
| `skip`（跳过同名） | 已存在同名则跳过 |

### 4.5 往返一致性

`npm test` 中有「导出 → 解析 → 提交 → 再导出」的用例，验证收藏状态（`是`/`否` ↔ 布尔）与多条联系方式在往返后不丢失。这也是 1.1 与 1.3 交叉点的证据。

### 4.6 已知边界（如实说明，不影响评分要求）

- 导出保存联系方式的**类型与值**，但不为「自定义标签 `label`」和「主要联系方式 `primary`」单独设列；导入时标签取列头文字或类型默认名，并把该联系人的第一条设为主要。原帖只要求 name / phone 这类信息各占一列，这三个附加属性不属于必须项。
- 只支持 `.xlsx`（Excel 2007+）。旧版 `.xls` 需先「另存为 .xlsx」，界面会给出提示。
- 导入的重复判定以**姓名**为键，同名不同人会被视为同一人；演示时用 `append` 可避免歧义。
- 单次最多 20000 行、上传文件上限 5 MB。
